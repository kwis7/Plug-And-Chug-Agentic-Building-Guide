# 2. 给工作一个可以继续的位置

完成的比较保存了一个答案。一个有用的工作空间还会保存理解答案所需的东西：输入、要求、检查，以及尚未完成的事项。缺少这些内容，下一次会话很容易重复调查，或者沿用一个已经忘记适用范围的结论。

我们的例子只需要一个小目录。给定笔记与工作结果、交接记录分开放置，仓库自带的 `expected/` 保留为教学参考。这样的安排不需要新建 Agent、数据库，也不必先生成完整项目骨架。

## 让每个文件有明确用途

来源笔记说明提供了什么资料。`workspace/comparison.md` 是草稿；复核后，`outputs/comparison.md` 成为检查过的答案。`workspace/handoff.md` 记录当前状态和下一项允许执行的动作。这些文件各有用途，草稿并不是最终结果的第二个权威版本。如果决定变化，先复核修改，再更新结果，并在交接记录中写清状态。

工作增加以后，下面几种区别会越来越有用：

| 信息类型 | 回答的问题 | 例子 |
|---|---|---|
| 来源资料 | 提供了什么证据？ | Cedar Hall 记载的开放时间 |
| 任务状态（task state） | 现在做到哪里？ | 比较已检查，尚未联系场地 |
| 记忆（memory） | 哪条简短线索有助于恢复工作？ | 当前任务位置与关键决定 |
| 知识（knowledge） | 哪种稳定认识值得复用？ | 证据缺失如何影响比较判断 |
| 技能（skill） | 哪种做法应该重复使用？ | 逐一检查候选项是否满足每项要求 |

**上下文（context）**则是另一个概念：它指当前会话实际交给模型的材料。文件存在于磁盘上，不代表已经进入上下文。“请读取来源”这条指令，也不同于来源已经被读取的证据。需要确认加载情况时，让 Agent 指出支持答案的文件及其中的事实。

## 保留来源，也保留未知

不要为了让比较更容易，把 Maple 的来源笔记改写成一个确定答案。输入中保留“入口情况未说明”，在结果中解释这会如何影响判断。如果后来取得新证据，记录它的来源和日期，再更新受影响的判断。这样不必保存整段聊天，也能追溯结论为什么变化。

真实工作同样如此。摘要是对来源的解释，不能取代来源信息。分开记录资料的说法与自己的结论，保留足够的出处，让复核者能检查两者之间的推理。只保存你有权保留、并且有权交给工具使用的材料。

## 有需要时，再增加结构

标准项目骨架为较大的工作提供了约定位置：`raw_data/` 保存原始输入，`workspace/` 放草稿，`artifacts/` 放生成的中间产物，`logs/` 记录执行轨迹，`outputs/` 放经过检查的结果，`archive/` 保存已结束的材料。完整职责见[文件系统契约](../../../skills/portable-agentic-system/pas/references/filesystem-contract.md)。

这些名称表达用途，但不会执行权限控制。一个能读取整个目录的工具，仍然可能接触名叫 private 的文件。因此，敏感工作需要实际的访问限制，并明确决定哪些资料可以进入模型。公开示例应当使用合成或获准公开的内容，不能只是把私人记录换掉名字。

增加文件夹之前，先做一个简单测试：能否在一分钟内找出当前答案、它的来源和下一步？如果可以，现有结构也许已经足够。如果不行，就解决造成耽搁的具体歧义。每一层结构，都应当降低继续工作的成本。
