# 4. 把有效的方法留下来

做过几次比较后，你可能发现，真正值得保留的是流程：先明确要求，再从每份来源提取相同字段，逐项判断，并展示证据缺口。场地、文档和当前模型都可以变化，这套方法仍然有用。

**Skill 的核心是一份 Markdown 指令文档**，通常命名为 `SKILL.md`。宿主加载它以后，其中的文字就成为模型上下文的一部分。你把好用的提示词或方法放到一个容易发现的位置，就像把操作手册“置顶”（pin），方便以后重复使用。模型依靠已有能力遵循这份说明；保存 Skill 本身不会训练新的模型权重。

这里的“置顶”是为了找回方法，不代表每轮都加载全文，也不自动提高指令优先级。名称和描述帮助宿主选择，完整流程与参考资料按需加载。Skill 还可以附带示例、模板或脚本，但脚本仍然需要实际工具和执行权限。当重复工作或反复出现的错误值得专门处理时，维护一项 Skill 才有意义。

## 提炼方法，留下具体案例的边界

“选择 Cedar Hall”是一次虚构练习的结论；“检查每个候选项是否满足所有必要条件”才是可复用的方法。把两者混在一起，下一次比较就可能继承旧答案。

针对这项练习，可以这样描述一个有用的 Skill：

```text
名称：有来源支持的比较
适用情况：根据明确要求，比较用户提供的候选项。
输入：要求与具名来源笔记。
方法：提取事实并标注来源；逐项检查要求；
区分满足、不满足和未知；解释最终判断。
输出：简短比较、待解决问题和交接记录。
限制：不推测缺失事实，不执行外部动作。
```

这只是教学示例，不是可在所有工具中直接安装的通用格式。仓库的 [Skill 模板](../../../skills/portable-agentic-system/pas/templates/skill/SKILL.md)展示了打包形式。能否被发现和加载，取决于所选运行环境与安装位置。

## 让触发条件真正帮助选择

描述应当让系统在加载完整内容之前，就知道何时使用这项方法。“帮助研究”太宽泛，无法说明它与摘要、写作、数据收集有何区别。有效的描述会写清工作类型、输入、输出与不适用情况。

用几条普通请求试一试。“根据我们的要求比较这三份供应商资料”应当选中比较方法；“写一封感谢信”不应当选中。“比较这些场地并预订最合适的一个”包含两个不同动作：Skill 可以完成比较，而预订需要单独的能力和授权。触发一个流程不能悄悄扩大权限。

然后检查方法本身。场地练习应当得到三个不同判断：Cedar 有证据支持，Willow 时间不符，Maple 的无障碍条件待确认。再加入缺失来源或信息冲突的变化，看看流程是否正确处理不确定性，而不是只会复述参考答案。

## 把经验放到合适的位置

始终适用的偏好，应当进入相关工作规则。稳定背景进入知识。今天尚未完成的比较进入任务状态。反复执行的步骤进入 Skill。真正需要执行或访问外部服务的能力，由工具承担。

这样分开以后，Skill 才容易理解和维护。短描述用于发现，主体说明方法，详细参考只在任务需要时加载。每轮对话都加载所有 Skill 和参考材料，会消耗注意力，也破坏这种按需使用的安排。

## 共享做法，同时保留数据归属

另一个 Agent 可以借用比较方法，而不必收到私人候选资料、内部决定或完整聊天记录。分享流程和合成示例，再由接收方提供自己的获准输入。方法因此能够传播，数据归属也仍然清楚。

新 Skill 应在实际使用后复查。针对可识别、可复现的问题保留修正，不必把每个特殊请求都变成永久规则。更详细的[方法提炼指南](../../../skills/portable-agentic-system/pas/references/skill-distillation-and-fusion.md)说明了如何保留重复经验，同时避免积累大量重叠流程。
