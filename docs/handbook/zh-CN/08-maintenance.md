# 8. 维护真正用得上的积累

工作空间应当随着有用成果的积累，变得更容易继续使用。把所有内容都存下来，并不能自动达到这个目标。未经整理的聊天记录、重复流程、过期状态页和失效指令，反而可能让下一次会话更慢、更不可靠。

维护可以从一个实际问题开始：哪些保留的信息有助于未来任务，它们应放在哪里？保留决定、出处、有效方法和恢复线索。当材料所在的位置不再适合它的用途时，再移动、归档或退役。

## 把当前任务收好

场地比较结束后，保留具名来源、检查过的答案、相关验证说明和交接记录。没有必要把每个草稿都放进紧凑记忆。如果一次纠正揭示了可复用的经验，再判断它是否应补充到已有 Skill 或知识笔记中。

不是每个任务都需要修改记忆。记忆是简短的恢复辅助：当一个长期决定或线索否则难以重新找到时，它才有价值。当前进度留在任务里，大段解释放进知识或可引用的产物中。

使用标准项目骨架时，更新任务记录，再重新生成 `STATUS.md`，不要在多个位置分别维护进度。任务结束后，把最终结果和剩余限制写清楚，避免后来的读者把旧草稿误认成正在执行的任务。

## 根据真实摩擦做维护

维护频率应反映使用情况。经常使用的系统可以每周做一次简短检查；不常打开的项目，也许重新使用时检查即可。文档里写了一张时间表，只能算建议，直到实际配置并测试了调度器，才能称为已启用的自动任务。

寻找重复出现的问题：不断重讲背景、找不到来源、职责分配不清、启动文件过大、跳过验证、多个副本相互矛盾。修复造成问题的最小原因。一项 Skill 描述不清，可能只需要改一句话，不一定需要新 Agent 或新框架。

较大的调整可以留下简短的前后记录。例如：“新会话原来会读取整个归档；入口现在只指向当前任务，需要时再检索旧笔记。”然后在新会话中检查实际行为。只修改了指令，最多能证明文字发生变化。

## 控制启动时加载的内容

工具包为指令、记忆、任务记录和大文件索引设置了容量限制，目的是鼓励按需加载。它们并不意味着每个文件填满额度，效果就会更好。

文件过大时，先保护信息意义，再压缩长度。稳定解释移到知识，任务细节回到各自任务，已结束历史进入归档，启动位置保留简洁线索。不要为了通过大小检查，删除某个未解决决定的唯一记录。

大输入应有清单，记载路径、大小、用途和加载策略。模型可以先看索引，再读取相关部分，而不是一次读完整个资料库。受限材料仍然需要真正的访问控制；清单不是权限系统。

## 保持结构变化可恢复

合并 Agent、停用 Skill 或移动权威文件之前，先确认负责人、引用关系、活跃任务和恢复路径。适当保留可恢复版本，并为破坏性或外部动作取得所需授权。整齐的目录不能取代可理解的历史。

[系统复查与更新指南](../../../skills/portable-agentic-system/pas/references/system-review-and-renewal.md)提供更深入的做法。等积累足够真实使用经验后再展开评估。很多时候，最好的维护结果是系统更小了，而留下的每一部分都有清楚用途和实际价值。
