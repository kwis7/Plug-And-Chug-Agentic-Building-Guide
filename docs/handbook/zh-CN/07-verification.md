# 7. 分清到底完成了哪一步

“完成”可能表示文件已经生成、比较已经复核、测试已经通过，也可能表示某个外部动作已经成功。这些结论需要不同证据。可靠的工作方式，会在开始前说明期望结果，再检查与该结果对应的事实。

对于场地练习，完成意味着比较符合给定笔记、判断遵循明确要求、未知项仍然可见，并且留有可用的交接记录。它不意味着工作坊已经有了确认预订的场地。最终回复和下一次会话都应保留这个区别。

## 让检查对应声明

| 想要声明的结果 | 应当检查的证据 |
|---|---|
| 结果已保存 | 打开准确的文件并查看内容 |
| 比较有证据支持 | 把关键事实与判断逐一追溯到来源 |
| 脚本检查通过 | 记录命令、退出状态和相关输出 |
| 文档可以使用 | 渲染、检查页面，并测试导航 |
| 运行环境加载了指令 | 观察新会话是否使用预期入口 |
| 完成关卡生效 | 在实际环境中观察无效与有效案例 |
| 外部动作成功 | 核对服务的权威结果或回读记录 |

**验证记录（receipt）**保存实际发生的事情：做了什么检查、何时进行、输入是什么、相关工具版本、结果，以及证据位置。任务文件里写着一条计划运行的命令，不算验证记录。小型比较可能只需要简短复核说明；后果更重的工作，则可能需要测试日志、文件哈希、截图或独立复核。

自动检查擅长发现明确条件，例如文件缺失或状态页过期。它不一定能发现流畅文字中的错误解读。在我们的例子里，检查是否出现“无障碍”三个字，远弱于检查 Maple 的无障碍条件是否被正确标为未知。

## 区分文字指令与实际约束

一条指令可以要求 Agent 在预订前停下。受限的工具策略可以让它无法调用预订操作。校验器可以拒绝缺少证据的任务记录。运行环境的 hook 可以接收校验器结果并采取动作，但前提是接入已经被加载，而且实际行为符合预期。

这些机制相互配合，却不能互相替代。仓库的完成关卡（closeout gate）检查输出是否存在、验证状态是否已声明、记录路径是否有效、状态页是否最新、容量限制是否符合要求，以及任务锁是否释放。它不会独立判断报告中的每个结论是否真实。错误或不诚实的“passed”记录，仍然需要内容复核来发现。

运行环境也必须正确连接关卡。在终端里运行脚本并得到错误，不能证明宿主会阻止最终完成声明。这需要用一个故意不完整的任务，再用一个有效任务，在新会话中测试。静态证据与实际运行证据应分开保存。

## 让部分完成仍然有用

如果 Maple 的来源无法读取，就说明哪些内容检查过，哪些尚未核实。如果任务要求的是忠于证据的比较，那么“入口情况未知”可以是正确的最终结果。如果任务要求确认每个选项的无障碍条件，同一个缺口就会阻止完成。决定这一点的是任务约定。

无法继续时，保留可用文件，说明依赖什么，并写出下一步。适当时使用如实的失败或取消状态。不要为了通过关卡、或让看板显得整齐，编造成功记录。

好的验证让下一位使用者知道：可以依赖什么，应当检查什么，以及哪些新证据可能改变结论。[可靠性参考](../../../skills/portable-agentic-system/pas/references/textbook-reliability.md)进一步解释了任务、验证记录、完成关卡和恢复机制。
