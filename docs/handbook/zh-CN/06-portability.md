# 6. 把工作带到另一个工具中

可迁移的工作，应当在原对话之外仍然容易理解。场地笔记、比较、交接记录和可复用方法，都能由人阅读，也能提供给另一个模型。这是可迁移性的基础。自动加载、工具访问和规则执行，则需要额外适配。

更换模型与更换运行环境是不同的操作。**模型（model）**负责推理；**服务提供方（provider）**通过服务或后端提供推理能力；**运行环境（runtime）**承载会话、组装上下文、提供工具，并可能管理权限或钩子（hook）。**切换层（switchboard）**可以管理模型或服务配置，却不因此拥有任务记录和工作文件。

## 先确定哪些东西需要带走

从最小但有用的一包材料开始：任务要求、获准使用的来源、当前结果、交接记录，以及相关方法。再加入影响这项工作的规则。目的工具支持上传大量文件，不代表应该上传整个私人工作空间。

接着确认目的工具如何接收这些内容。本地工具可能识别指定入口文件；托管工作空间可能要求填写项目指令并上传选定文件；自行开发的 API 应用则需要自己组装上下文、实现保存逻辑。一份写着“请读取我的文件”的文档，不能让本来没有文件访问能力的界面突然获得这种能力。

还要决定修改如何回到权威工作副本。如果新工具只在聊天中给出修改后的比较，就需要有人保存回去。没有对齐规则的两份副本，即使各自模型推理正确，也会逐渐分歧。人工写回完全可以是一种有效流程，前提是分工明确。

## 把兼容性记录当作证据说明

仓库的[兼容性清单](../../../skills/portable-agentic-system/pas/compatibility/runtime-compatibility.json)记载了产品类别、生成的配置、限制和证据状态。其记录的审查日期为 2026-08-09。在这份记录中，Codex、Claude Code 和 Gemini CLI 被标为 `verified_static`，新会话验证为 `not_run`。这描述的是仓库保存的证据，并不表示本手册重新认证了厂商当前的产品行为。

其他条目还区分已文档化的接入、人工映射（manual projection）、暂定支持、模型服务、切换层和自建 Harness 模式。适配文档有参考价值，但文件存在不能证明产品已经加载它，或已经执行其中的规则。先读[适配选择指南](../../../skills/portable-agentic-system/pas/references/adapters.md)，再读目标工具的适配文件。安装或改变接入方式时，还应重新核对该产品的官方说明。

## 用小练习检查目的环境

迁移重要工作前，先用合成的场地练习。在目的环境中新开会话，分别检查四件事：

1. 能否识别预期规则和具名来源文件。
2. 能否正确完成比较，并保留 Maple 的入口未知项。
3. 能否把结果与交接保存到约定位置，或者明确说明保存由你完成。
4. 如果声称存在机械完成检查，能否拦下故意不完整的任务，并放行有效完成的任务。

记录工具版本、日期、测试材料、观察结果和剩余缺口。模型说“我理解规则”，不能证明完成关卡真的生效。另一方面，没有关卡不妨碍人工复核一份比较；它改变的是你能声明到哪一步，以及哪些检查需要自己承担。

在新路线通过检查前，保留原工作副本。迁移的目标，是带走已有证据和方法，同时调整依赖具体运行环境的部分。长期材料和迁移限制都清楚，可迁移性才真正可用。
