# 5. 职责开始冲突时，再拆分工作

一个 Agent 配合几项合适的 Skill，已经可以承担相当多的工作。出现新主题或新的写作格式，并不自动意味着需要另一个 Agent。当反复进行的工作具有不同使命、数据边界、来源体系、权限或交付周期时，拆分才开始有价值。

先想清楚要避免哪种问题。如果研究结论还在变化，设计者却同时修改最终报告，明确划分职责可能有帮助。如果问题只是表格格式不一致，模板或 Skill 往往已经足够。

## 选择合适的组织单位

| 实际需要 | 通常可以从这里开始 |
|---|---|
| 一个临时目标 | 任务或项目 |
| 跨任务重复的方法 | Skill |
| 稳定的参考材料 | 知识集合 |
| 有独立归属的长期工作 | 领域 Agent |
| 一项边界清楚的独立贡献 | 临时子 Agent（subagent） |
| 访问服务或执行具体动作 | 工具或连接器（connector） |

领域 Agent 表示一种持续的职责，通过指令、工作文件和访问安排体现出来。它不必永久绑定某个模型。换一个模型，改变的是当前推理组件，不应悄悄改变资料归谁负责，或者哪些动作获得了授权。

场地练习只需要一个 Agent。更大的长期活动工作流，可能由研究方维护来源比较，再由沟通方准备获得批准的消息。调查选项与联系场地有不同的权限要求。职责分开后，边界更容易检查，但实际工具权限与明确的行动规则仍然必要。

## 委派之前，先写清责任

一项清楚的委派，应说明需要什么结果、能读哪些输入、可以在哪里写入、哪些动作禁止，以及如何检查产出。只有“研究一下”四个字，会留下太多不同理解的空间。

例如，可以请一名临时复核者读取三份虚构笔记，指出 `workspace/comparison.md` 中缺乏支持的判断。它需要读取这些文件，并有一个提交复核意见的位置；无需改写来源、改变任务范围或联系场地。主任务仍然负责整合意见、检查最终答案，再保存到 `outputs/comparison.md`。

当一个看似合理的错误可能逃过自查时，独立复核尤其有用。但它也增加时间与上下文成本，应当有具体理由。第二个 Agent 如果只重复相同假设、没有查来源，并不会显著增加可信度。

## 同一权威文件只安排一个写入者

两个 Agent 可以读取同一来源。两个 Agent 同时修改同一份当前状态，却可能互相覆盖。给每条权威路径安排一个写入者，其他参与者另写建议或产物。

Git worktree 可以把并行代码修改放在不同检出目录中。资源锁（resource lock）用于协调共享文件、设备、端口等资源的占用。它们处理的问题不同：worktree 不会隔离共享账户，锁也不是隐私保护。两者都不会授予发布或执行外部动作的权限。

当多个长期负责人需要路由或协调时，中控才开始有用。它负责知道工作归谁、管理依赖、整合结果，但不会因此自动拥有每个领域的私密事实。不同 Agent 可以共享方法，数据则只在获得授权的范围内传递。

## 用普通请求测试职责边界

为每个 Agent 写两条明确属于它的请求、两条不属于它的请求，再写一条与相邻职责重叠的请求，检查描述能否合理分配工作。[路由评估指南](../../../skills/portable-agentic-system/pas/references/description-routing-evals.md)提供了更完整的方法。

如果无法说明新增 Agent 为什么需要独立责任，就先把任务留给现有负责人。等拆分能让一个真实边界更清楚时再增加结构，并始终为每份最终结果保留一个明确的主负责人。
