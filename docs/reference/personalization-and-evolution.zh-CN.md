# 把有用的偏好留下来，也能检查、修改和撤回

[English](personalization-and-evolution.md) | [中文](personalization-and-evolution.zh-CN.md) · [首页](../../README.zh-CN.md)

继续使用你已有的通用 AI Agent。它的原生运行环境（native harness）负责加载指令、使用工具、管理权限和执行任务。本地工作空间给你允许使用的资料、有效方法、偏好和未完成的工作一个能查看、能续用的位置。这份指南补充一个小规模的偏好复查流程，不要求另建执行平台或记忆引擎。

如果还在考虑资料该放在哪里，先看[本地工作空间指南](local-workspace.zh-CN.md)。偏好只是其中一部分。个人原始资料仍由你控制，只使用你为本任务提供的最少字段、明确授权并标为 agent-readable 的脱敏衍生资料，或只输出这些必要字段的受控中介结果。本地保存本身不能阻止应用或云端模型接收你交给它的内容。

## 从一句明确的话开始

你可以说：“以后比较来源时，先给简短建议，再解释依据和未知项。请把这个偏好保留给比较任务使用。”

助手应记录你提出的要求、适用范围和存放位置。这种明确的未来使用指令，可以授权它在指定范围内保留偏好；同一范围已经同意过，就不必反复确认。它不应据此推断你的性格，也不应修改无关说明。

小工作空间里，在 owner 现有的项目说明或知识文件中留一条简短记录，可能就够用了。需要版本、复查队列或静态检查时，再考虑正式 JSON 记录。两种做法都不需要新增 Agent、数据库，或替代现有应用的原生功能。

## 先分清，这次反馈是什么意思

- **只改这一次：** “把这次回答缩短。”在当前任务中执行，必要的进度也留在任务里。它不自动成为长期偏好。
- **明确要求以后使用：** “以后比较来源，都按这个开头。”有保留授权时，才在指定范围内保存；范围不清楚，就先澄清这一部分。
- **反复出现的纠正：** 类似请求多次出现，可以提出候选。次数本身不代表保留许可，不能证明稳定偏好，也不能让它自动适用于所有任务。

不要为了发现偏好而自动挖掘私人聊天记录、扫描个人文件夹。只使用用户提供的最小反馈，或明确授权且允许 AI 读取的摘要。本地偏好不能扩大读文件、使用工具、连接账户或执行外部动作的权限，也不能覆盖上层规则或降低证据要求。

## 一个够用的生命周期

**记录候选 → 检查冲突 → 按需试用 → 在指定范围内启用 → 回滚或退役。**

1. **记录候选。** 写清 owner、希望采用的做法、适用任务、不适用任务、日期和最小来源指针。候选放在 owner 现有的 workspace。事实、未解决问题和一次性纠正留在对应任务里；可复用程序进入 Skill。
2. **检查冲突。** 对照现有指令、已启用偏好和授权边界，把检查结果记为 `pending`、`passed` 或 `conflict`。冲突解决后再启用。偏好记录不是修改安全规则或权限的入口。
3. **按需试用。** 如果用途或范围尚不确定，记为 `trial`。用无敏感资料的小例子检查要求的格式，再用一个相邻任务检查是否误用。新会话是否实际加载了正确版本，应单独观察。没有实际运行过的检查，仍标为 `not_run`。
4. **启用已获授权的偏好。** `active` 表示 owner 同意在未来匹配的任务中使用它，需要保留授权、来源不是 `one_off`，并且冲突检查通过。明确的未来使用指令可以授权启用，不必编造试用记录。启用只记录未来采用的安排，不能证明应用实际加载过，也不能证明输出质量更好。
5. **有记录地回滚。** 修改做法或范围之前，先保留旧版本。写明要恢复哪个更早版本、为什么恢复，再把 owner 的相关索引或指令指向它。被替换版本记为 `retired`，说明原因；两个版本都保留，让变化可追溯。
6. **不再适用时退役。** 用户可以撤回偏好、改变适用范围，或停止使用。把状态改为 `retired`，记录原因，从未来任务采用的偏好集合中移出；保留简短恢复指针，不删除唯一历史。复查频率按实际使用确定，这份指南不会自动启用定时任务。

开始一个匹配任务时，让助手读取具名的 active 偏好、检查范围，并说明用了哪个版本。不适用的任务不应套用它。当前任务的明确请求，可以在上层规则允许的范围内覆盖普通格式偏好，但不应悄悄改写长期记录。

## 例子：比较任务先给建议

下面是一段虚构过程，不是已经观察到的改进：

- **原来：** 比较先写几段背景，最后才给建议。
- **用户反馈：** “以后比较来源，先用两句短话给建议，再列来源和未知项。请保留给比较任务使用。”
- **候选：** owner 为 `example-owner`，偏好 ID 为 `source-comparison-opening`，版本为 `1`；适用于 `source-comparison`，不适用于 `creative-writing` 和 `debugging`。
- **期待的下一次成果：** 在现成的虚构场地练习中，开头说明 Cedar 符合已记录需求、列为候选，同时保留 Maple 无台阶入口未知；后面再列来源表。没有新增场地事实，也没有声称可以预订。
- **本次例外：** “这一次先探索可能性，不急着推荐。”只调整本次呈现，不自动退役长期偏好。
- **以后修改：** 用户要求改变未来默认做法时，保留版本 `1`，提出版本 `2`，复查适用范围，并指明可用于回滚的更早版本。

<summary>可选：使用带版本的 JSON 记录和静态检查</summary>

[偏好记录模板](../../skills/portable-agentic-system/pas/templates/preference-record.json)是一份虚构候选：保留授权为 `false`，冲突检查为 `pending`，证据类型为 `illustrative`，验证记录列表为空。作为自己的记录使用前，把 owner、示范做法、来源指针和日期换成获得授权的信息。

这份记录包括：

- **身份：** `schema_version: 1`、`kind: preference`、稳定的 `id` 和 `owner`，以及正整数 `version`。
- **状态：** `proposed`、`trial`、`active` 或 `retired`。
- **范围：** 具名的 `include_task_types`、可选的 `exclude_task_types`，以及希望采用的 `behavior`。
- **来源与授权：** `source.kind`、最小 `reference`、采用 `YYYY-MM-DD` 的 `recorded_at`、`retention_authorized` 和 `conflict_review`。
- **版本关系：** `supersedes_version` 和 `rollback.restore_version` 指向更早的正整数版本，或保留为 `null`；回滚要有理由，退役记录必须填写 `retirement_reason`。
- **证据：** 编写的示例用 `illustrative`，实际观察用 `observed`。`evidence.receipt_refs` 填验证记录的 ID，不填文件路径。需要检查版本关系时，相关验证 JSON 必须一起明确提供；检查器不会自行搜集私密证据。

需要检查现成模板时，可以让助手从仓库根目录执行：

```bash
python3 scripts/check_workspace_records.py \
  skills/portable-agentic-system/pas/templates/preference-record.json
```

命令只读取具名记录并报告静态问题，不修改记录、不启用偏好、不改变设置，也不运行模型。检查验证记录之间的引用时，要明确提供相关文件。静态通过不能证明应用加载了记录、遵守了范围，或改善了成果。

保留授权与实际加载证据应分开。真正的观察记录应标明偏好 ID 和版本、使用的应用或运行环境、具名输入，以及实际检查了什么。不要把示范记录或准备执行的检查写成已观察的证据。

偏好采用 `evidence.mode: observed` 时，检查器要求非空的验证记录列表，并且这些实际观察记录必须明确提供，与偏好 ID 和版本一致。已获授权的 `active` 偏好，在没有声称实际加载过时，可以保留为 `illustrative`，不填写验证记录。
